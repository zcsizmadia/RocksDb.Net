# RocksDb 11.12.0 — i7-12800H

```text
BenchmarkDotNet v0.15.4, Windows 11 (10.0.26200.9457)
12th Gen Intel Core i7-12800H 2.40GHz, 1 CPU, 20 logical and 14 physical cores
.NET 10.0.14, X64 RyuJIT x86-64-v3
Job=ShortRun  IterationCount=3  WarmupCount=3
```

**ShortRun numbers again**, so the same caveat as the 11.8.1 file: read the
allocation columns, which are exact, and treat the timings as order of
magnitude.

## How this was compared

The 11.8.1 file recorded only the callback and event-listener suites, so it
could not answer the question this run exists for. Each suite below was
therefore run twice on the same machine on the same day: the `v11.8.1.3` tag
against RocksDb 11.8.1, and this upgrade against 11.12.0. The difference
between the columns is the native bump plus this release's wrapper changes,
which is what someone upgrading gets.

## Verdict

**No regression.** Every allocation is identical, apart from a sub-kilobyte
wobble in the listener suite. Every timing difference is inside the 11.12.0
run's own error bar. The 11.12.0 column is a few percent slower in more rows
than it is faster, and the biggest gap, 16 KB `GetPinned`, sits under an error
bar larger than the measurement. That is not a finding at three iterations,
but it is the place to look first if a full run is ever made.

`MultiGet` now uses one native allocation per batch instead of one per value
found. At 128 keys of 256 bytes on an in-memory database that does not show:
the per-value allocation was a small part of the call, and the managed
allocation is unchanged by design.

## Event listeners

| Method | Flushes | 11.8.1.3 | 11.12.0 | Error (11.12.0) | Allocated |
| --- | --- | ---: | ---: | ---: | ---: |
| Flushes with no listener attached | 20 | 15.68 ms | 14.14 ms | ±2.602 ms | 173.25 KB |
| Flushes with a listener that overrides nothing | 20 | 13.04 ms | 14.12 ms | ±6.940 ms | 355.57 KB → 354.99 KB |
| Flushes with a listener subscribed to nothing | 20 | — | 19.34 ms | ±53.851 ms | 173.34 KB |
| Flushes with a listener that overrides five events | 20 | 13.55 ms | 15.95 ms | ±6.338 ms | 355.58 KB → 355 KB |

The listener rows differ from the 11.8.1 file, which recorded a listener that
overrides nothing allocating the same 173 KB as no listener. Here it allocates
as much as one overriding five events, at `v11.8.1.3` as well, and that is by
design rather than a regression. The 11.8.1 file was recorded under the
reflection gate, which skipped any event whose virtual was not overridden. The
same day, #156 replaced it with `EventListener.Subscribed`, which defaults
to every event so that a listener cannot go silent by forgetting to declare
one. A listener that overrides nothing therefore now receives, and builds the
info objects for, every event, unless it narrows `Subscribed`; the saving is
still there, but it is opted into. The benchmark's "overrides nothing" row
predates that and does not narrow it.

The "subscribed to nothing" row was added in this release to measure the
saving as it now exists, so it has no 11.8.1.3 figure. It allocates what no
listener does, which is the 11.8.1 file's "overrides nothing" result, reached
the way the API now asks for it. Its timing is from a separate, noisier run.

The callback suite likewise allocates 109.38 KB at both versions, against
101.56 KB in the 11.8.1 file, so that file predates a change to the read path
it measures rather than recording something this upgrade altered.
